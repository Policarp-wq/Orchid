# Orchid Remote: data contract and definition of done

Status: proposal. The mock in `Orchid.Remote/wwwroot/mock/` implements the client-visible part of this contract, so the page in `Orchid.Remote/wwwroot/` already runs against it. The server, the session controller and the PC panel are not implemented. Visual reference: `remote-mockup.html`.

## 1. What this is

A phone or tablet page that **controls** the PC app on the same LAN: Start/Stop, BPM, pulse, plus a read-only view of elapsed recording time and session state.

Not in scope: beat or tick display, key presses, note data, recording playback, audio. The metronome click and MIDI capture run on the PC; the page never touches timing.

Principles that every item below follows:

1. **The PC is the only source of truth.** The phone shows the last state it received and sends commands. It never keeps its own session.
2. **Elapsed time on the phone is display only.** It is interpolated from the last snapshot and is never used to timestamp notes.
3. **Plain HTTP on the LAN.** The page runs in an insecure context, so it must not use `crypto.randomUUID`, `crypto.subtle`, the Screen Wake Lock API or the Clipboard API. `crypto.getRandomValues` is available.
4. **Commands go through the same code path as the PC buttons.** A remote Start must behave exactly like pressing Start session in the window (same locks, same validation).

## 2. Data definitions

### 2.1 Pairing code

| Property | Rule |
| --- | --- |
| Alphabet | `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (32 symbols; `I O 0 1` excluded) |
| Length | 8 symbols, 40 bits, from a CSPRNG (32 divides 256, so no modulo bias) |
| Display | `XXXX XXXX` on the PC |
| Input | accepted case-insensitively; spaces and `-` are stripped before validation |
| Lifetime | 5 minutes from creation |
| Use | single use: consumed when a valid pairing request is created, not when it is approved |
| Active codes | at most one; "New code" invalidates the previous one |
| Failure response | wrong, expired and used codes are indistinguishable (`404 invalid_code`) |
| Lockout | 5 `invalid_code` failures from any client within 60 s lock pairing for 5 minutes (`429 too_many_attempts`, `retryAfterSec`); the PC panel shows the lock. `invalid_format` does not count |

### 2.2 Pairing request

| Field | Type | Rule |
| --- | --- | --- |
| `requestId` | string | 8 random bytes as 16 hex chars, unguessable |
| `status` | enum | `pending`, `approved`, `denied`, `expired` |
| `verification` | string | `<Word> <NN>`, word from a fixed list of at least 8 words, `NN` in 10..99; generated by the PC and shown identically on the PC and the phone |
| `deviceName` | string | from the client; control characters and `<` `>` removed, trimmed, max 40 chars, fallback `Unknown device`; shown on the PC as plain text only |
| `ip` | string | remote address seen by the server, shown on the PC |
| TTL | | 2 minutes; becomes `expired` |
| Concurrency | | at most one `pending` request; another valid code while one is pending returns `409 request_pending` |
| Decision | | only the PC UI can approve or deny; the phone can only cancel its own request |
| Token delivery | | the token is returned exactly once, in the poll that first sees `approved` |

### 2.3 Device and token

| Field | Rule |
| --- | --- |
| `token` | 32 random bytes as 64 hex chars; sent as `Authorization: Bearer <token>`; the PC stores only a hash and compares in constant time |
| Device record | `id`, `name`, `ip`, `connectedAt`, `lastCommand { type, at }` |
| Lifetime | until revoked, or sharing is turned off, or Orchid exits, or 8 hours pass without an authenticated request |
| Revocation | the next request from that device returns `401 unauthorized`; the phone shows "Device removed" within 2 s |
| Limit | at most 3 paired devices; a fourth approval is refused on the PC with a visible message |

### 2.4 Session state (`GET /api/state`, also returned by every command)

| Field | Type | Rule |
| --- | --- | --- |
| `version` | int | `1`. Clients ignore unknown fields; removing or re-typing a field bumps it |
| `status` | enum | `idle`, `recording`, `stopping` |
| `elapsedMs` | int ≥ 0 | `recording`: milliseconds since the recording began. `stopping`: frozen final value. `idle`: duration of the last recording, `0` if none; kept until the next start |
| `serverTimeMs` | int | PC clock at snapshot time, informational |
| `bpm` | int | 30..240, the same value the PC tempo field uses |
| `pulseDenominator` | int | one of `1 2 4 8 16`, the same value as the PC pulse picker |
| `strongBeats` | bool[] | one flag per beat of the measure (the length equals `pulseDenominator` in the current 4/4 scope; another meter gives another length); `true` plays the strong click. Default is `[true, false, ...]`. Any subset is valid, including none and all |
| `meter` | string | `"4/4"` (fixed in this version) |
| `midiInput` | string or null | display name of the selected input, max 80 chars, `null` if none |
| `canStart` | bool | `status == idle && midiInput != null` |
| `locked` | bool | `status != idle`; BPM and pulse cannot change |
| `error` | null or `{ code, message }` | `midi_disconnected`, `recording_failed`; cleared by the next successful start |

Invariants: `elapsedMs` does not decrease during one recording. `strongBeats.length == pulseDenominator` in every state. `bpm`, `pulseDenominator` and `strongBeats` never differ from the PC window's values by more than one poll interval.

### 2.5 Command (`POST /api/command`, JSON)

```json
{ "type": "setBpm", "commandId": "9f2c7a3b61d84e05", "bpm": 124 }
```

| `type` | Extra fields | Precondition | Effect | Errors |
| --- | --- | --- | --- | --- |
| `start` | none | `status == idle` and `midiInput != null` | begins recording exactly like Start session on the PC | `409 already_recording`, `409 locked_while_recording` (stopping), `409 no_midi_input` |
| `stop` | none | `status == recording` | ends recording, keeps it in memory | `409 not_recording` |
| `setBpm` | `bpm` integer | `status == idle` | sets BPM | `409 locked_while_recording`, `422 bpm_out_of_range` (not an integer, or outside 30..240) |
| `setPulse` | `pulseDenominator` integer | `status == idle` | sets pulse and resets `strongBeats` to the default for the new length | `409 locked_while_recording`, `422 pulse_invalid` |
| `setStrongBeats` | `strongBeats` bool[] | `status == idle` | replaces the whole pattern; the length must equal the current `pulseDenominator` | `409 locked_while_recording`, `422 strong_beats_invalid` (not an array of booleans, or wrong length) |

`commandId`: 8..64 chars from `[A-Za-z0-9-]`, unique per command. The server remembers the last 50 per device. A repeated id returns `200` with the current state and does **not** apply the command again, so a retry after a lost response is safe.

### 2.6 Error body

```json
{ "error": { "code": "bpm_out_of_range", "message": "BPM must be between 30 and 240.", "retryAfterSec": 300 } }
```

`retryAfterSec` appears only on `429`. `message` is for logs; clients map `code` to their own text.

| HTTP | `code` |
| --- | --- |
| 400 | `invalid_format`, `invalid_command`, `unknown_command` |
| 401 | `unauthorized` |
| 404 | `invalid_code` |
| 409 | `request_pending`, `already_recording`, `not_recording`, `locked_while_recording`, `no_midi_input` |
| 413 | `payload_too_large` |
| 422 | `bpm_out_of_range`, `pulse_invalid`, `strong_beats_invalid` |
| 429 | `too_many_attempts`, `rate_limited` |

A network failure on the client has no HTTP status; the client treats it as code `network`.

### 2.7 Endpoints

| Method and path | Auth | Request | Response |
| --- | --- | --- | --- |
| `POST /api/pair/request` | none | `{ code, deviceName }` | `202 { requestId, verification, expiresAt }` |
| `GET /api/pair/{requestId}` | none | | `200 { status, token? }` |
| `DELETE /api/pair/{requestId}` | none | | `204` (cancels a `pending` request) |
| `GET /api/state` | bearer | | `200` State |
| `POST /api/command` | bearer | Command | `200` State |
| `DELETE /api/session` | bearer | | `204` (this device disconnects) |
| `GET /` and static files | none | | the page |

### 2.8 PC panel model (what the MAUI window needs to show)

```text
RemoteAccess
  sharing        bool                       off at every app start
  address        string or null             "http://192.168.1.23:47318" while sharing
  pairingCode    { value, expiresAt } or null
  lockedUntil    ms epoch or null           pairing lockout
  pendingRequest { requestId, deviceName, ip, verification, createdAt } or null
  devices[]      { id, name, ip, connectedAt, lastCommand { type, at } or null }
```

Actions: toggle sharing, new code, approve, deny, revoke. Turning sharing off closes the listener and invalidates all tokens.

## 3. Behavior rules

- BPM, pulse and strong beats are locked while `status != idle`, on the PC and over the network. A command that tries to change them gets `409 locked_while_recording` and changes nothing.
- If the MIDI input disappears while recording, the PC stops the recording, keeps what was captured, and reports `error.code = midi_disconnected` in the next state.
- `stopping` lasts only until the recording is closed and stored; it is part of the contract so the phone can disable Start during it.
- Start, stop and settings changes made on the PC window appear on the phone within one poll interval.

## 4. Security requirements

Each one is testable.

1. The token travels only in the `Authorization` header. No cookies are set or read.
2. A request with an `Origin` header that does not match the server's own origin is rejected. Commands require `Content-Type: application/json`. No CORS headers are sent.
3. Codes and tokens come from a CSPRNG. Tokens are stored hashed and compared in constant time.
4. The listener exists only while sharing is on, and is bound to the active private IPv4 address, not to all interfaces.
5. `POST /api/pair/request` obeys the lockout in 2.1. Authenticated endpoints allow at most 20 requests per second per device, then `429 rate_limited`.
6. Request bodies over 1 KB are refused with `413`.
7. Codes and tokens are never logged and never appear in URLs.
8. Device names are rendered as plain text everywhere on the PC.
9. Known and accepted risk: the connection is unencrypted. Someone on the same network who captures a token can send the four commands above. Mitigations are idle expiry, revocation, and sharing being off by default.

## 5. Client rules (the page)

- Poll `GET /api/state` every 1 s while the page is visible, and immediately when it becomes visible again.
- Three consecutive network failures show "Connection lost". A `401` shows "Device removed" with no reconnect, only a new code.
- Elapsed time is `elapsedMs` plus time since the snapshot was received, while `status == recording`.
- The control screen shows only a summary of the strong beats and an Edit button. Edit opens the shared modal with the shared beat bars (UI-SPEC "Shared components"). A change sends the whole new pattern with `setStrongBeats`, debounced like BPM. Selecting a new pulse rebuilds the open bars from the default pattern the server returns. If the PC starts recording while the modal is open, the bars become disabled.
- BPM buttons: one change per tap, press and hold repeats after 400 ms every 80 ms, the request is sent 300 ms after the last change and carries the final value.
- Touch targets at least 48 px, text contrast at least 4.5:1 in light and dark, works from 320 px width without horizontal scroll.
- Display text is not hard-coded in logic: every visible string, accessible name and error text comes from a message catalogue keyed by id, with English as the source. The server sends language-neutral `code` values and never display text. The language follows `navigator.language` with an override; numbers and times use `Intl`. The shared components use the same key names as the PC app (IMPLEMENTATION-DOD D11). The mock page currently keeps its strings in `remote.js` and `index.html`, which is the thing to replace.

## 6. Definition of done

### Data and logic (server and controller)

- [ ] State serializes exactly the fields in 2.4, with the stated ranges, and passes a schema check in a test.
- [ ] `start`, `stop`, `setBpm`, `setPulse` follow the table in 2.5 for every listed error, one test per row.
- [ ] A command and the same action on the PC window run the same code. Starting from the phone yields a recording whose note timings share one origin with the metronome, indistinguishable from a PC start.
- [ ] Changing BPM, pulse or strong beats on the PC shows on the phone within 1 s, and the other way round.
- [ ] The pattern from `strongBeats` is the one the metronome plays: with beat 3 only strong at pulse 1/4, clicks 1, 2, 4 are weak and click 3 is strong in every measure. Covered by the same tests as the PC pattern in IMPLEMENTATION-DOD D2.
- [ ] `setPulse` resets the pattern to the default; `setStrongBeats` with a wrong length is refused and changes nothing.
- [ ] Unplugging MIDI while recording stops the recording and the phone shows the error within 1 s.
- [ ] Repeating a `commandId` does not repeat the effect.
- [ ] Pairing code: alphabet, length, normalization, 5 minute expiry, single use, and the 5-failures-in-60-s lockout are covered by unit tests.
- [ ] Pairing request: one pending at a time, 2 minute expiry, token delivered once, device name sanitized, cancel works.
- [ ] Revoking a device makes its next request return `401`. Turning sharing off closes the listener (no listening socket on the port) and invalidates every token.
- [ ] Every security item in section 4 has an automated test or a recorded manual check.

### PC panel

- [ ] Shows address, code with countdown, pending request with the verification word, device list; every action in 2.8 works.
- [ ] The verification word on the PC equals the one on the phone for the same request.
- [ ] Lockout, port-in-use and "no network" are visible states, not silent failures.

### Page

- [ ] All four views work: enter code, waiting for approval, control, connection lost / device removed.
- [ ] The strong-beats modal opens from Edit, edits any beat, follows a pulse change from the PC while open, dismisses by its close button, Escape and the backdrop, and locks while recording. The components in `components/` have no dependency on the rest of the page.
- [ ] Every error code in 2.6 that a user can trigger has human text.
- [ ] Uses no secure-context-only API (checked on a phone over plain HTTP).
- [ ] Switching the page language changes every visible string, accessible name and error text; a check fails when a key is missing in a language or display text appears outside the catalogue. English and Russian are delivered.
- [ ] Works on a real phone over Wi-Fi against the real server, in light and dark.

## 7. What the mock covers

`Orchid.Remote/wwwroot/mock/mock-api.js` and `mock-pc.js`, served by any static server (the mock folder is deleted when the real client replaces it).

| Covered | Not covered |
| --- | --- |
| State shape including `strongBeats`, all command validation and errors (including `strong_beats_invalid`), idempotent `commandId`, locks while recording | Token hashing, constant-time compare |
| Pairing code format, TTL, single use, lockout; request TTL, one pending, device name sanitizing | Origin checks, body size limit, per-device rate limit, idle expiry, device limit |
| Approve, deny, cancel, revoke from a mock PC panel | The real MAUI PC panel |
| MIDI unplug while recording, network drop, sharing off | Real network behavior, firewall, port conflicts |
| All four page views and the control flow | Verification on a real phone |

## 8. Open decisions

| Item | Proposal |
| --- | --- |
| Port | default `47318`, configurable, error shown in the panel if busy |
| Idle token expiry | 8 hours |
| Device limit | 3 |
| Poll vs push | polling at 1 Hz in this version; push (SSE or WebSocket) only if polling proves too slow |
| Meter | fixed `4/4`; add a field only when the PC UI supports other meters |
